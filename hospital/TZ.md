# Техническое задание: три интерфейса системы управления пациентами

Команда: **Бекаман, Данияр, Далел**. Репозиторий: [diko-cat/maz](https://github.com/diko-cat/maz).

## 1. Задача текущего занятия

Подготовить frontend-проект на Next.js **без бэкенда**, оформить техническое задание в Markdown и реализовать три варианта одного интерфейса: **Tailwind CSS**, **Bootstrap** и **MUI**. Использовать существующий GitHub-репозиторий `maz` и приложение в папке `hospital`.

Результат задания — локальная учебная демонстрация на вымышленных данных. Исходный план более широкой системы сохранён ниже как архивный материал. Его требования не входят в это задание и не являются обязательными следующими этапами.

## 2. Технологии и маршруты текущего этапа

- Next.js App Router, React и TypeScript.
- Tailwind CSS — первый вариант интерфейса.
- Bootstrap — второй вариант интерфейса.
- MUI и Emotion — третий вариант интерфейса.
- Общие типы данных, бизнес-логика и клиентское хранение для трёх вариантов.

| Маршрут | Назначение |
| --- | --- |
| `/` | Интерфейс по умолчанию на Tailwind CSS |
| `/tailwind` | Вариант Tailwind CSS |
| `/bootstrap` | Вариант Bootstrap |
| `/mui` | Вариант MUI |

Внутри каждого варианта доступны разделы «Обзор», «Пациенты», «Врачи» и «Записи на приём». Переход между библиотеками сохраняет общие данные в пределах одного браузера и адреса приложения.

## 3. Функциональные требования текущего этапа

### Обзор

Показывать количество пациентов, врачей, записей и приёмов на текущий день. Показатели вычислять из текущего набора данных. Отображать ближайшие приёмы и последних пациентов с переходами к соответствующим разделам.

### Пациенты

- Таблица с ФИО, датой рождения, полом и контактами.
- Поиск по ФИО без учёта регистра.
- Фильтр по полу и сортировка по ФИО или дате регистрации.
- Добавление и редактирование через форму: ФИО, дата рождения, пол, телефон, электронная почта.
- Проверка обязательных полей, корректности даты рождения, телефона и необязательной электронной почты.
- Уникальный идентификатор новой записи.
- Удаление с подтверждением и согласованное обновление связанных записей на приём.
- Понятное пустое состояние, если пациентов нет или поиск не дал результатов.

### Врачи

Показывать вымышленных врачей, их специальность, кабинет и доступность. Предусмотреть поиск по имени и специальности. Изменение списка врачей не входит в задание.

### Записи на приём

Показывать пациента, врача, дату, время и статус. Позволять создавать запись с выбором существующего пациента и доступного врача. Проверять обязательные поля и занятость выбранного врача. Предусмотреть отмену записи и обновление показателей обзора.

## 4. Данные и ограничения

Пациенты и записи на приём сохраняются в `localStorage` браузера. После перезагрузки они доступны в том же браузере и на том же адресе. Между разными устройствами, браузерами или портами данные автоматически не синхронизируются. При отсутствии сохранённых данных используются демонстрационные примеры.

Бэкенд не разрабатывается: серверное API, база данных и авторизация не требуются. Роли пользователей, медицинские документы и публикация приложения также не входят в задание. Использовать только вымышленные данные. Вся прикладная логика работает в браузере; dev-сервер Next.js используется для разработки и запуска интерфейса.

## 5. Требования к интерфейсу

Три варианта должны использовать соответствующие библиотеки и давать одинаковые основные возможности. Допускаются разные цвета, композиция и оформление компонентов. Обязательны адаптация под узкие экраны, читаемые таблицы, подписи полей и кнопок, управление с клавиатуры, состояния пустого поиска и обратная связь после действий.

## 6. Критерии приёмки текущего этапа

1. Проект устанавливается и запускается по README.
2. Маршруты `/tailwind`, `/bootstrap` и `/mui` открываются напрямую; между ними есть переключатель.
3. Все три варианта содержат обзор, пациентов, врачей и записи на приём.
4. Поиск, фильтр по полу и сортировка пациентов работают совместно.
5. Пациента можно добавить, изменить и удалить с подтверждением; некорректная форма показывает ошибки.
6. Можно создать и отменить запись на приём; конфликт занятости врача обрабатывается.
7. Изменения доступны после обновления страницы и перехода в другой вариант интерфейса.
8. Показатели обзора соответствуют данным; при отсутствии данных показываются понятные сообщения.
9. Выполнены `npm test` (даты, валидация пациентов и конфликты расписания), `npm run lint` и `npm run build`; фактические результаты фиксируются при сдаче, а не предполагаются заранее.

## Проект: система управления пациентами больницы

### 1. Цель проекта

Разработать веб-приложение для управления информацией о пациентах и врачах больницы, а также для организации записей на приём.

Система должна предоставлять сотрудникам удобный интерфейс для просмотра, добавления, редактирования и поиска пациентов, просмотра списка врачей и управления записями на приём.

Разработка будет проходить поэтапно. На первых этапах используются моковые данные, чтобы реализовать и проверить интерфейс и основную логику приложения без подключения базы данных. 

### 2. Технологический стек

* **Next.js** — разработка веб-приложения.
* **React** — создание компонентов интерфейса.
* **TypeScript** — типизация данных и уменьшение количества ошибок.
* **Tailwind CSS** — стилизация интерфейса.
* **Lucide React** — иконки.
* **PostgreSQL** — база данных на последующих этапах.
* **Prisma ORM** — работа с базой данных.
* **Git и GitHub** — контроль версий и хранение исходного кода.
* **Vercel** — размещение приложения на последнем этапе.

Версии библиотек и инструменты настройки проекта фиксируются в `package.json` и файле блокировки зависимостей.

### 3. Основной функционал

#### 3.1. Главная страница

Создать главную панель управления (Dashboard), которая содержит:

* общее количество пациентов;
* общее количество врачей;
* количество записей на приём;
* количество приёмов на текущий день;
* быстрые ссылки на основные разделы приложения.

Показатели должны формироваться на основе имеющихся данных. Если данных нет, отображаются нулевые значения и понятное пустое состояние.

#### 3.2. Список пациентов

Создать страницу `/patients` со следующими возможностями:

* отображение списка пациентов в виде таблицы;
* отображение основных данных: ID, ФИО, дата рождения, телефон и дата регистрации;
* переход к просмотру карточки пациента;
* переход к редактированию пациента;
* удаление пациента с подтверждением действия;
* переход к форме добавления нового пациента.

Если список пуст, пользователь должен увидеть сообщение об отсутствии пациентов и кнопку добавления.

#### 3.3. Добавление пациента

Создать страницу `/patients/new` с формой регистрации пациента.

Поля формы:

* фамилия — обязательное поле;
* имя — обязательное поле;
* отчество — необязательное поле;
* дата рождения — обязательное поле;
* пол — необязательное поле;
* номер телефона — обязательное поле;
* электронная почта — необязательное поле;
* адрес проживания — необязательное поле.

Требования:

* проверка обязательных полей;
* проверка корректности даты рождения;
* проверка формата электронной почты и номера телефона;
* отображение ошибок рядом с соответствующими полями;
* сохранение данных после успешного заполнения;
* отображение уведомления об успешном добавлении;
* отмена создания с возвратом к списку пациентов.

Для каждого пациента система должна формировать уникальный идентификатор.

#### 3.4. Редактирование пациента

Создать страницу `/patients/[id]/edit`.

Функционал:

* загрузка текущих данных пациента;
* отображение данных в форме;
* редактирование доступных полей;
* повторная проверка введённых значений;
* сохранение изменений;
* отображение уведомления об успешном сохранении.

Если пациент с указанным ID не найден, приложение должно показать соответствующее сообщение и предоставить возможность вернуться к списку.

#### 3.5. Удаление пациента

Реализовать удаление пациента из списка.

Требования:

* перед удалением показывать диалог подтверждения;
* отображать предупреждение, что действие повлияет на доступность данных пациента;
* при отмене не изменять данные;
* после подтверждения удалять запись из текущего набора данных;
* обновлять список и показатели Dashboard.

На этапе моковых данных допускается удаление из состояния приложения. После подключения базы данных способ удаления необходимо согласовать с правилами хранения медицинских данных. Для реальной системы предпочтительно предусмотреть архивирование вместо безвозвратного удаления.

#### 3.6. Поиск и фильтрация пациентов

На странице `/patients` реализовать:

* поиск по фамилии, имени и отчеству;
* поиск без учёта регистра;
* фильтрацию по полу, если поле используется;
* фильтрацию по дате регистрации;
* сортировку по ФИО и дате регистрации;
* кнопку сброса фильтров.

Поиск и фильтрация должны работать совместно. Если совпадений нет, отображается сообщение «Пациенты не найдены».

#### 3.7. Врачи

Создать страницу `/doctors`.

Для каждого врача отображать:

* ID;
* фамилию и имя;
* специальность;
* контактный телефон;
* статус активности.

На первом этапе список врачей заполняется моковыми данными.

Функции:

* просмотр списка врачей;
* поиск по имени и специальности;
* просмотр подробной информации о враче;
* выбор врача при создании записи на приём.

Добавление, редактирование и удаление врачей могут быть предусмотрены как следующий этап развития проекта, если сроки первой версии ограничены.

#### 3.8. Записи на приём

Создать страницы `/appointments` и `/appointments/new`.

Форма записи должна содержать:

* пациента;
* врача;
* дату приёма;
* время приёма;
* причину обращения (необязательно);
* статус записи.

Возможные статусы:

* запланирована;
* подтверждена;
* завершена;
* отменена.

Функции:

* просмотр списка записей;
* создание новой записи;
* выбор пациента из списка;
* выбор врача из списка;
* просмотр даты и времени приёма;
* фильтрация по врачу, пациенту, дате и статусу;
* отмена записи;
* проверка занятости врача на выбранное время.

Нельзя создавать две активные записи к одному врачу на пересекающиеся временные интервалы. На первом этапе эта проверка реализуется в клиентской логике, а после подключения базы данных должна также выполняться на сервере.

До подключения базы данных все функции должны работать с локальным набором тестовых данных.

* использовать единые функции для поиска и фильтрации;

Важно: изменения в обычном React-состоянии могут пропадать после перезагрузки страницы. Если необходимо сохранять данные между перезапусками браузера, можно временно использовать `localStorage` для учебной версии. После подключения базы данных источником данных становится сервер.

Для демонстрации использовать только вымышленные данные пациентов.
